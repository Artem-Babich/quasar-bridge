# Дополнения форка

Руководство автора переехало в [wiki](https://github.com/skrashevich/quasar-bridge/wiki). Здесь — только то, что добавлено в форке Artem-Babich/quasar-bridge.

Кнопки (`button`) мост тоже нажимает: например, «покорми котов» нажмёт кнопку
кормушки. Разрешайте для Assist только те кнопки, которые можно нажимать голосом.

### Контекст для выбора маршрута (форк)

С `routing.classifier.route_context: true` классификаторы (Decisions и запасной
LLM) вместо диалога выше читают отдельную запись: последние 3 хода всех маршрутов
за последние 2 минуты. Реплика ассистента помечена обработчиком: `[yandex]`,
`[home]` или `[llm]`; музыка и управление плеером считаются `[llm]`. Так короткий
ответ на вопрос Яндекса возвращается к Яндексу:

```text
user: Заведи таймер
assistant: [yandex] На какое время поставить таймер?
user: На 30 секунд
```

В запись попадают только доставленные на колонку финальные ответы с текстом.
Диалог LLM для ответов не меняется: команда другого маршрута по-прежнему его
завершает, а реплики Яндекса и дома в него не попадают.

Запись живёт в оперативной памяти, отдельно для каждой колонки, и подчиняется
`dialogue_context`: при `enabled: false` её нет, а при `ttl_seconds` меньше 120
она исчезает раньше двух минут. Фраза «начни новый разговор» стирает и её.
Если в записи или в диалоге есть личная история, оба классификатора получают только фразу.

⚠️ Реплики Яндекса и дома уходят в OpenAI и к провайдеру LLM. Вместе с этим полем
нужен промпт, который объясняет пометки, поэтому по умолчанию оно выключено.


При долгом ответе маршрута `llm` прослушивание запрашивается уже в начале
потокового ответа: колонка планирует его оттуда, и слушать она начнёт только
после речи. Другие маршруты в начале потока его не запрашивают. Если к этому
моменту уже поставлен беззвучный запуск музыки, запроса тоже нет. ⚠️ Музыка,
которую инструмент поставит позже, этого не отменит: начальный конверт уже ушёл.


### Список покупок через LLM

Фразы о списке мост не разбирает: маршрут выбирает Decisions, а `todo.shopping_list`
ведёт LLM через два инструмента ha-mcp.

```json
{
  "llm_chat_parameters": { "max_tokens": 4096 },
  "assistant_tools": {
    "enabled": true,
    "web": false,
    "history": false,
    "time": false,
    "parallel_calls": true,
    "max_rounds": 5,
    "max_calls": 10,
    "mcp_servers": [
      {
        "name": "ha",
        "transport": "streamable_http",
        "url_env": "QUASAR_HOME_MCP_URL",
        "allowed_tools": ["ha_get_todo", "ha_set_todo_item"],
        "timeout_ms": 5000,
        "max_result_chars": 3000
      }
    ]
  }
}
```

Когда среди разрешённых инструментов есть `ha_set_todo_item`, мост добавляет к
системному промпту правила списка. `parallel_calls: true` разрешает модели несколько
вызовов за шаг: иначе длинный список упрётся в `max_rounds`. Выполняются вызовы всё
равно по очереди. Настройка действует только на ответы LLM, а не на планирование
дома.

Поднимите `max_tokens`: вызовы одного шага считаются одним ответом модели. С
лимитом 1024 вычёркивание восьми позиций обрывается, и мост получает пустой ответ.

В промпте классификатора список покупок относится к маршруту `llm`. Удаления нет:
«удали» вычёркивает позицию, полностью очистить список можно в приложении HA.
Пустой `allowed_tools` открывает модели все инструменты сервера, поэтому оставьте
оба имени явно.


Если классификатор выбрал `llm`, а фраза — явная команда включить музыку с сайта,
музыка запускается напрямую, как при совпавшем правиле с маршрутом `llm`.


| `route_context` | `false` | Читать [записанные ходы всех маршрутов](#контекст-для-выбора-маршрута-форк) вместо диалога LLM; применяется по `SIGHUP` |
| `decisions_timeout_ms` | `0` (= 1500) | Только с `classifier_api: "decisions"`: время на ответ Decisions, от 0 до 60000 мс и меньше `timeout_ms` (0 считается как 1500), иначе конфиг не принимается; весь шаг классификации всё равно не дольше `timeout_ms` |

### Классификатор на OpenAI Decisions (форк)

По умолчанию маршрут выбирает тот же LLM, что отвечает (`classifier_api: "llm"`).
С `classifier_api: "decisions"` несовпавшую фразу сначала классифицирует
[OpenAI Decisions API](https://developers.openai.com/api/docs/guides/decisions)
(один вопрос `choice` с вариантами `home`, `llm`, `yandex`, инструкция —
`classifier.prompt`). Если Decisions вернул ошибку HTTP, отказ, неизвестный
маршрут или не уложился в `decisions_timeout_ms`, маршрут выбирает LLM-классификатор
как обычно; если и он не смог — применяется `on_error`.

| Поле верхнего уровня | По умолчанию | Назначение |
| --- | --- | --- |
| `classifier_api` | `llm` | `llm` или `decisions` |
| `classifier_base_url` | — | Обязателен для `decisions`, например `https://api.openai.com/v1` |
| `classifier_model` | — | Обязателен для `decisions`, например `gpt-6-luna` |

Поля верхнего уровня можно задать и переменными `QUASAR_CLASSIFIER_API`,
`QUASAR_CLASSIFIER_BASE_URL`, `QUASAR_CLASSIFIER_MODEL` (они перекрывают JSON, даже
пустые). Порядок включения, проверки и отката — в
[decisions-classifier.md](decisions-classifier.md).

Ключ — переменная `QUASAR_CLASSIFIER_API_KEY` в `runtime.env`; без неё
конфигурация с `decisions` отклоняется. Поля верхнего уровня применяются после
перезапуска, `decisions_timeout_ms` — по `SIGHUP`. При `llm` адрес и модель
Decisions игнорируются.

Ограничения:

- уверенность (`confidence`) только пишется в лог и не влияет на маршрут;
- в Decisions уходит та же инструкция и история, что и LLM-классификатору,
  кроме приватной истории (после поиска по истории запросов уходит только фраза);
- сбой Decisions добавляет до `decisions_timeout_ms` перед LLM-классификатором;
- запущенный мост держит соединение тёплым: сразу при старте и раз в 60 с он
  делает `GET /models/{classifier_model}` тем же клиентом. Это не вызов Decisions,
  токены он не расходует; ответ не важен, в журнал попадает только смена статуса
  (`decisions_keep_warm`, 0 — ответа нет). `-route` и `-check-backends` так не делают;
- старый бинарник без этих полей не запустится с такой конфигурацией.

В журнале `native_route_decision` и в выводе `-route` у решений классификатора
есть `backend` (`decisions` или `llm`), `latency_ms`, `confidence` и
`error_class` (почему не ответил Decisions: `http_<код>`, `transport`, `timeout`,
`canceled`, `refusal`, `bad_response`). `-check-backends` дописывает в конец строки
`; Classifier: decisions ok, route …, confidence …, cold N ms new connection, warm M ms reused connection (timeout T ms)`
и завершается с ошибкой, если Decisions не ответил. При старте в журнал пишется
строка `classifier_backend` с бэкендом, моделью и тайм-аутом (без ключа).
В строке решения также есть `decisions_ms`, `conn_reused`, а при сбое `error_code`
и `request_id`.

| `llm_answer_model` | `QUASAR_LLM_ANSWER_MODEL` | Необязательная модель для ответов на вопросы, тот же API и ключ; `llm_model` остаётся для дома и выбора маршрута. Пусто — `llm_model` везде; требуется перезапуск |

### YouTube Music (форк)

Единственный канал музыки — [ytm-alice](https://github.com/SPAWNRYS-ban/ytm-alice) на самой колонке.
Мост понимает фразу и отдаёт плееру одну команду через его панель; сам ytm-alice фразы не слушает.

**Колонка.** Нужен ytm-alice с переключателем `YTM_ALICE_VOICE=0` (копия 0.7.6 с правкой) и официальный
пакет для модели колонки (из него берутся проигрыватель и resolver):

```sh
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -trimpath -ldflags='-s -w' -o ytm-alice .   # в source/ копии ytm-alice
scripts/ytm-alice/install.sh ytm-alice-0.7.6-bergamot.yampkg ./ytm-alice root@SPEAKER BRIDGE_IP 2222
```

Скрипт кладёт файлы в `/data/ytm-alice`, ставит автозапуск `/etc/init.d/S99zytm-alice` с перезапуском после
сбоя, выключает трансляцию с телефона и фразу «Включаю», а панель (порт 24721) открывает только для `BRIDGE_IP`.
Медиаслой Bluetooth не ставится, поэтому кнопка паузы на колонке YouTube не управляет. Удаление —
`scripts/ytm-alice/uninstall.sh root@SPEAKER 2222` (`--purge` удалит и аккаунт с очередью).
Вход в аккаунт — по коду YouTube TV в панели ytm-alice.

**Мост.** В `runtime.env` задайте адрес панели:

```sh
QUASAR_YTMUSIC_URL=http://SPEAKER:24721
```

С ним классификаторы получают маршрут `music`, а слоты музыки и управления занимает YouTube вместо музыки
с сайтов. В промпт классификатора добавьте строку `music` и метку `[music]` в описание истории, уберите
музыку из `yandex`. Если в `routing.rules` есть правило вроде `yandex_services` со словами «музыку», «песню»,
«трек», уберите эти слова: правила проверяются раньше классификатора. Слова плеера («пауза», «продолжи музыку»)
мост проверяет до правил, поэтому `speaker_playback` трогать не нужно. Адрес панели — только IP колонки:
панель ytm-alice отвечает лишь на свой адрес. Без переменной всё работает как раньше.

| Что сказали | Что происходит |
| --- | --- |
| музыкальная фраза (выбирает классификатор) | поиск в YouTube Music, ответ «Включаю: исполнитель — трек.» |
| «включи музыку» | рекомендации |
| «мои лайки», «включи лайки» | лайки (нужен вход) |
| «пауза», «продолжи», «играй», «дальше», «назад», «хватит», пока музыка звучит | команда плееру, ответ без речи |
| «дальше», «назад», «продолжи» в тишине или на паузе | продолжить сохранённую очередь, «Сейчас ничего не играет.» или «Нечего продолжать.»; при открытом разговоре с LLM — в разговор |
| «пауза», «хватит» в тишине или на паузе | Яндексу: может звенеть будильник или таймер |
| «что играет» | исполнитель и трек или «Сейчас ничего не играет.» |
| «лайк», «дизлайк» во время музыки | молча пропускаются |
| оба классификатора недоступны и фраза начинается с «включи», «поставь» | «Не удалось понять, что включить. Повтори, пожалуйста.» |

Пока музыка звучит, микрофон после ответов моста не открывается (на паузе — открывается). Команда музыке не
сбрасывает разговор с LLM. Ответы YouTube в истории для классификатора помечены `[music]`. Состояние плеера
мост спрашивает не дольше секунды и не спрашивает для запросов, ушедших Яндексу.
